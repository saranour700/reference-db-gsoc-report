1. Project Overview

The goal of this project was to design and implement a maintainable Reference Database pipeline for Canadian food products.

The Reference DB is intended to provide a structured, traceable, and reusable representation of food products collected from heterogeneous Canadian sources. The project focuses on transforming source-specific product data into a common model while preserving source provenance and avoiding loss of source-level information.

The pipeline was designed to separate:

  • source extraction and ingestion,
  • data standardization and validation,
  • product identity and normalization,
  • classification and taxonomy,
  • product grouping,
  • variant representation,
  • nutrition data,
  • scores and enrichment,
  • and production-ready outputs.

A central design principle throughout the project was that source data should not be silently rewritten or merged just because two products belong to the same product group.

Product identity, variants, and source-level information are therefore represented separately.

2. Project Goals

The main objectives of the project were to:

  1. Design a scalable architecture for a Canadian Reference DB.
  2. Support multiple heterogeneous product sources through a retailer-adapter architecture.
  3. Standardize source data into a common schema.
  4. Preserve source IDs, provenance, and source-level values.
  5. Build a product identity and grouping pipeline.
  6. Separate core product identity from variant-level attributes.
  7. Add classification and taxonomy information.
  8. Integrate nutrition and scoring data into the production pipeline.
  9. Add validation, data contracts, and quality statuses.
  10. Produce reproducible and maintainable outputs for future contributors and downstream applications.
  11. Document the architecture, decisions, limitations, and future work.

3. What Was Implemented

The main implemented work includes:

  • retailer-adapter architecture and a shared ingestion layer (dlt + DuckDB);
  • source-to-common-schema standardization;
  • validation and data quality checks;
  • product identity normalization;
  • deterministic product grouping;
  • candidate generation and ambiguity handling;
  • rule-based classification and taxonomy;
  • product variant generation;
  • nutrition integration;
  • Nutri-Score component calculation, score eligibility, and category-level Agribalyse mapping;
  • production output generation;
  • versioned data contracts (YAML specifications) and phase-level validation;
  • automated tests;
  • end-to-end QA;
  • and project documentation.

The core pipeline was implemented and validated on the Compliments dataset, while additional Canadian source data was collected and evaluated as part of the broader project.

4. Final Architecture

The implemented pipeline is organized into logical phases:

Retailer Source
          ↓
Retailer Adapter
          ↓
Ingestion (dlt → DuckDB raw layer)
          ↓
Phase 1 — Validation
          ↓
Phase 2 — Identity & Normalization
          ↓
Phase 3 — Classification / Taxonomy / Grouping
          ↓
Phase 4 — Variant Generation
          ↓
Phase 5 — Nutrition Enrichment
          ↓
Phase 6 — Scores / Additional Enrichment
          ↓
Production Outputs

Each phase is currently run as a separate step; running the full pipeline as one managed workflow is listed under future work (Section 22.6).

Technology stack: Python, dlt (ingestion), DuckDB (raw storage), pandas and Parquet (phase outputs), Hugging Face Hub (dataset storage and publishing), pytest and ruff (testing and linting).

Retailer-specific logic is isolated in the adapter layer, and the processing phases are designed to be retailer-agnostic. Each phase receives a defined input representation, performs its own responsibilities, and produces an output representation for the next phase. The expected input and output of each phase is described by a versioned data contract.

This separation is intended to make the pipeline easier to maintain, test, extend, and validate as additional sources and processing requirements are introduced.

5. Adapter Architecture and Ingestion

Retailer Adapters

Source-specific differences are handled in retailer adapters, which sit at the boundary between a source and the pipeline.

All adapters implement a common interface (RetailerAdapter) that exposes:

  • retailer — the retailer name;
  • products() — standardized product records;
  • nutrition() — standardized nutrition records.

The adapter contract (retailer_adapter.yaml) defines the common product and nutrition schema that an adapter must produce. Adapters are responsible for:

  • mapping source fields to the common schema;
  • preserving source identifiers and provenance;
  • normalizing field names and basic data types;
  • keeping products and nutrition as separate datasets.

Adapters explicitly do not classify products, assign taxonomy, create groups or variants, calculate scores, or perform entity resolution. Those responsibilities belong to the processing phases.

Ingestion

The shared ingestion step loads adapter output into the DuckDB raw layer using dlt. Ingestion is append-only and detects new products by the key (retailer, retailer_product_id). Detection of product updates and deletions is intentionally outside the current scope, as stated in the ingestion contract.

Phase Boundaries

The processing phases do not contain retailer-specific logic. The boundary between phases is described by data contracts, and each phase validates its own input and output. Phase 1 performs the generic mapping from the common ingestion schema to the Phase 1 schema (for example retailer_product_id → external_id, retailer → source_retailer, product_name → title, upc → barcode).

This design provides a foundation for future cross-source integration, including Phase 7.

Current Source Coverage

The Compliments adapter is the currently implemented ingestion path in the Reference DB repository. It reads the raw products and nutrition datasets from Hugging Face through DuckDB and reports the retailer as sobeys.

The repository also contains module placeholders for Costco, Metro, Voilà, and Walmart. These modules are currently empty and establish the intended extension points only; they should not be interpreted as implemented adapters or scrapers.

Several additional source datasets were collected during the project without all of them being integrated into the current adapter-to-production path.

6. Data Processing Phases

Phase 1 — Validation

Phase 1 validates incoming records before they enter downstream processing.

Validation includes checks such as:

  • required columns;
  • expected data types;
  • duplicate detection;
  • schema drift;
  • source-key uniqueness;
  • and structural consistency.

Phase 1 is intentionally focused on structural validation rather than semantic interpretation.

Records are not silently discarded. Validation results and quality statuses are retained so that failures and warnings remain traceable.

The current Phase 1 result is WARNING rather than PASS. Required fields are complete and there are no duplicates, but several optional fields that are not available in the current ingestion schema (description, ingredients_text, nutrition_text, size_amount, size_unit) are entirely null. This is the intended behaviour of the quality status logic: optional-data gaps are reported without stopping the pipeline.

Phase 2 — Identity and Normalization

Phase 2 creates a standardized representation of product identity.

The identity layer separates information required to determine whether records represent the same underlying product from information that describes variants.

The normalized identity process considers attributes such as:

  • normalized brand and product line (for example Compliments Organic, Balance, Naturally Simple);
  • product name and a size-free core_title;
  • identity flags (organic, gluten-free, naturally simple, sugar-free, unsalted, lactose-free, peanut-free, plant-based, reduced sodium);
  • fat level and fat percentage;
  • flavour and formulation keywords;
  • and functional variants such as diaper size or bin-liner size.

A deterministic identity_hash (SHA-256 over these normalized attributes) is generated before grouping. Package size is deliberately excluded from the identity so that size differences do not split a product.

Missing source values are not invented during normalization. Source identifiers and provenance are preserved so that downstream processing remains traceable to the original source record.

Phase 3 — Classification, Taxonomy and Grouping

Phase 3 separates several related but distinct responsibilities:

Standardized Product
        ↓
Classification (food / non_food / unknown)
        ↓
Taxonomy (food products only)
        ↓
Candidate Generation
        ↓
Grouping Decision
        ↓
Product Group

Classification and taxonomy are deterministic, rule-based and use no machine-learning or LLM component. Classification assigns a product domain (food, non_food, or unknown). Only food products receive a taxonomy category; non-food products do not receive a food taxonomy, and products with an unknown domain are marked ambiguous.

The taxonomy has 22 categories (including ALCOHOLIC_BEVERAGES, BAKING_INGREDIENTS, and OILS_VINEGARS). Taxonomy assignment uses a tiered evidence strategy:

  1. semantic meaning-based rules (Tier 0), with narrow exclusions;
  2. explicit disambiguation rules;
  3. specific product phrases;
  4. generic category keywords;
  5. a precedence rule for frozen products;
  6. otherwise the product stays AMBIGUOUS rather than being assigned an arbitrary category.

Each result keeps its confidence, matched rule, status, resolution type, and candidate categories, so every decision can be traced.

The grouping process is built around candidate generation and deterministic decision logic (see Section 7). Fuzzy matching is used to find candidate pairs; the decision itself compares explicit identity attributes.

The grouping process distinguishes:

  • SAME — records can belong to the same product group;
  • DIFFERENT — the records should not be merged;
  • AMBIGUOUS — the available information is insufficient for a safe automatic decision.

Ambiguous grouping decisions go to a review queue and are not merged. Classification and taxonomy remain separate from product identity and grouping so that changes in taxonomy rules do not require rewriting the identity model.

Phase 3 writes six outputs: product_classification, product_taxonomy, taxonomy_review_queue, product_groups, grouping_review_queue, and grouping_contradictions.

7. Product Grouping

Product grouping was implemented as a dedicated processing stage.

The grouping process follows this flow:

Normalized Product Identity
          ↓
Candidate Generation
(blocking on the title prefix + title similarity ≥ 0.85)
          ↓
Deterministic Decision Rules
(SAME / DIFFERENT / AMBIGUOUS from identity attributes)
          ↓
Group Resolution (union-find)
          ↓
Validation
          ↓
group_id
  • Candidate generation. Products are blocked by the leading tokens of their core_title, and pairs inside a block are kept as candidates when their title similarity reaches the threshold. Similarity is only used to propose candidates.
  • Decision rules. For each candidate pair, the decision compares the functional variant and the identity attributes (identity flags, fat level and percentage, flavour, formulation). A conflict in any compared attribute gives DIFFERENT; missing evidence on one side gives AMBIGUOUS; full agreement gives SAME.
  • Resolution. SAME decisions are combined into groups using union-find. Products whose taxonomy is AMBIGUOUS are never merged and always stay as single-product groups.
  • Validation. Every product must be assigned to exactly one group, and no DIFFERENT pair may end up in the same group. Contradictions raise an error and stop the phase.
  • group_id. A deterministic 16-character hash of the sorted external_id values of the group members.

The system preserves distinct products while allowing records that represent the same core product to remain in the same group despite size differences.

An important result from the project was that no single field should be treated as the entire identity signal. UPC, title similarity, or brand alone are not sufficiently reliable for grouping heterogeneous retail data. The UPC is carried through the pipeline as barcode but is not used as a grouping signal.

9. Variant Representation

Variant handling was implemented as a separate phase after grouping.

The current model distinguishes:

  • group_id — the shared core product identity.
  • variant_id — a variant within that group, defined by the product's package/size attributes.

The variant_id is a hash of the group_id and a variant_key built from the parsed size attributes (count, amount and unit, quantity, or the raw size text; products with no parseable size share a nosize key).

For example, package sizes can belong to the same product group while remaining separate variants:

Smooth Peanut Butter
      │
      ├── 500 g
      ├── 1 kg
      └── 2 kg

These products share the same group_id and have different variant_id values.

The 4,440 products map to 4,320 variants. This means a variant is not strictly one SKU: when two products in the same group have the same size key, they share a variant_id. SKU-level records are still preserved, because metadata, nutrition, and scores are keyed by external_id, and the variant mapping links each external_id to its group_id and variant_id.

10. Important Clarification on Flavour and Formulation

One important distinction became clear during the project.

Although flavour can be considered a variant-level difference from a product-family perspective, in the current implementation flavour and formulation are part of the identity used in Phase 3.

Therefore:

  • different package sizes can remain within the same group_id;
  • flavour or formulation differences can result in different group_id values.

This reflects the current implementation rather than a general statement that every product-family attribute is represented as a variant_id.

Examples used for validation included:

  • Jelly Powder — different flavours;
  • Crumb Cake — different flavours;
  • Pie Filling — different flavours;
  • Peanut Butter — smooth vs. crunchy and different sizes;
  • Salsa Chunky — mild vs. medium.

These examples were curated to document how the current pipeline handles different types of product variation.

11. Nutrition Pipeline

Nutrition data is processed separately from product identity and grouping.

The production nutrition output contains 4,440 product records aligned with the validated Compliments product set. The product table drives the integration, so every product remains present even when no nutrition source record exists.

Of the 4,440 products, 2,935 (66.1%) have a matching nutrition source record (matched by exact external_id), and 1,505 have no source nutrition data.

Nutrition quality is assessed per record:

  • SUSPICIOUS — at least one value exceeds a plausibility threshold (calories > 1000, fat > 100 g, or protein > 100 g);
  • MISSING_FIELDS — at least one of the 17 nutrition fields is missing;
  • VALID — all 17 fields are present and no value is suspicious;
  • NO_SOURCE_DATA — the product has no nutrition source record.

Current quality results include:

Nutrition status Rows
MISSING_FIELDS 2,931
NO_SOURCE_DATA 1,505
SUSPICIOUS 3
VALID 1

MISSING_FIELDS is intentionally strict: a record is flagged when any of the 17 fields (including optional ones such as omega-3, omega-6, or sugar alcohols) is missing. It therefore does not mean the record is unusable. For example, Nutri-Score eligibility in Phase 6 depends on only six required fields.

Serving sizes are parsed into amount and unit. Values are normalized to per 100 g for mass-based servings and per 100 ml for volume-based servings. Mass and volume are kept separate and no density-based conversion is performed. Servings that cannot be parsed (57 records) are left un-normalized instead of being guessed.

These results are not treated as pipeline failures by default. They distinguish between:

  • missing source information;
  • incomplete nutrition fields;
  • suspicious values;
  • and valid nutrition records.

This preserves the difference between “the source does not provide the information” and “the pipeline failed to process the information.”

12. Scores and Enrichment

The final production pipeline also includes a score and enrichment layer. Scores are treated as an enrichment layer rather than being mixed into the core product identity.

The current production score output contains 4,440 product records and 39 columns.

Eligibility

A product is eligible for the Nutri-Score calculation only if it is a food product, is not in an excluded category, has nutrition source data, and has all six required per-100 g inputs (energy, sugars, saturated fat, sodium, fibre, protein).

The current eligibility validation identified:

  • 818 eligible products
  • 3,622 products not eligible

Each excluded product keeps an explicit exclusion reason (for example non-food, unknown domain, no source data, or missing required fields).

Nutri-Score (2023) components

The pipeline implements the 2023 Nutri-Score algorithm for general foods: energy, sugar, saturated fat, and salt points, plus fibre and protein points, using the official threshold tables and unit conversions (kcal to kJ, sodium to salt).

A final Nutri-Score grade also requires the fruit, vegetable and legume (FVL) percentage. That value is not available in the current source data, and the pipeline does not estimate it from taxonomy. As a result, the current version stores the calculated component points and a FVL_NOT_AVAILABLE status, and does not yet publish final A–E grades. This follows the project principle that missing information stays missing.

Because eligibility currently uses the per-100 g fields, volume-based products (such as beverages) are not covered, and special 2023 rules for beverages and for fats, oils, nuts and seeds are not implemented yet.

Agribalyse mapping

Each food product receives a category-level Agribalyse mapping derived from its taxonomy, with a confidence level (MEDIUM or LOW) and an explicit note. This is a broad proxy and not an exact product-level Agribalyse or Ciqual match. Taxonomy categories without a defined mapping are marked NOT_AVAILABLE, and non-food products are marked NOT_APPLICABLE.

14. Product Group Data Merging

The current pipeline intentionally does not merge all SKU-level information into a single canonical source record at the group level.

For example, if the 500 g, 1 kg, and 2 kg versions of a product contain slightly different source metadata or nutrition information, those source-level differences are preserved.

The current model is:

product_groups
      ↓
shared product identity

product_variants
      ↓
variant-level differences

product_metadata / nutrition / scores
      ↓
SKU-level information

The system currently does not select one SKU as a source of truth and copy its values to all variants.

A richer group-level merged representation remains a future improvement.

17. Important Design Principles

Several principles guided the implementation.

Preserve Raw Source Data

Raw source data is not silently rewritten.

Normalized and enriched representations are created as additional processing layers.

Keep Phase Responsibilities Separate

Each phase performs its own defined responsibility rather than mixing unrelated transformations.

Preserve Provenance

Source IDs, source values, and provenance remain traceable through downstream processing.

Missing Does Not Mean Zero

Missing information remains missing rather than being replaced with a guessed value. For example, the fruit/vegetable/legume percentage is not estimated, so no Nutri-Score grade is published without it.

Identity and Variants Are Separate

The product group represents shared identity, while variant-level differences remain explicit.

Similarity Is Not Proof

Similarity-based matching can help generate candidates, but it is not sufficient by itself to establish product identity.

Ambiguity Is Explicit

Uncertain cases should be isolated rather than automatically forced into an incorrect decision.

Validate Each Stage

Every processing stage should provide explicit validation rather than relying only on final output checks.

19. What Was Not Fully Completed and Known Limitations

Not every part of the broader data-collection and integration work was completed in the current production pipeline.

Full Implementation of All Source Adapters

The repository contains the extension points required to support multiple sources, but the implemented ingestion logic is currently centered on Compliments. The Costco, Metro, Voilà, and Walmart modules are empty placeholders.

Cross-Source Integration

The current pipeline validates and processes source datasets individually.

A dedicated cross-brand and cross-retailer integration phase remains future work.

Group-Level Data Merging

Variant/SKU-level information is preserved today.

A future group-level canonical merge remains to be implemented.

Stability of Group and Variant IDs

group_id is a deterministic hash of the group's member IDs, and variant_id is derived from group_id. They are reproducible for the same input, but they will change if a group's membership changes when new products are onboarded. A stable-ID strategy is needed before incremental or cross-source updates.

Grouping Coverage

Candidate generation blocks products by the leading tokens of the core title, so products with the same meaning but a different word order may never be compared and could remain in separate groups. The final SAME decision compares identity attributes among candidates that passed the similarity threshold; it does not independently re-verify the title text. Both points should be evaluated quantitatively (false merges and false splits) on additional data. Taxonomy-ambiguous products are kept as single-product groups by design.

Rule-Based Taxonomy

Taxonomy is deterministic and rule-based. Part of the Tier-0 rule set was created to resolve ambiguous cases while protecting products that were already stable, so some category choices are pragmatic rather than ontologically strict. The review queue preserves the remaining ambiguous cases.

Package Size Source

The source size field is not carried through the Phase 1 output, so size_amount and size_unit are empty. Package size and variant attributes are currently extracted from the product title. Propagating the original size string from the ingestion layer would improve variant quality.

Scoring Coverage

Final Nutri-Score grades are not published yet because FVL data is unavailable. Beverages and other volume-based products, and the special-category scoring rules, are not covered. The Agribalyse mapping is category-level only, and some taxonomy categories (for example beverages and canned goods) do not yet have a defined mapping.

Nutrition Coverage

Only 66.1% of products have a nutrition source record, and very few records have all 17 fields populated.

Broader Grouping Validation

The grouping system is currently strongly validated on the Compliments dataset.

More edge cases should be added as additional retailers and brands are onboarded.

Expanded Regression Coverage

The existing examples should continue to grow to cover new naming patterns, product representations, and ambiguous cases.

Broader Production Integration of Collected Datasets

Several independently collected datasets are available as source assets, but they are not all connected to the current adapter-to-production path.

22. Future Work

22.1 Phase 7 — Cross-Brand and Cross-Retailer Integration

The next major phase would be the implementation of Phase 7, whose main purpose is to integrate the product data produced across all brands and retailers into a unified Reference Database.

The current pipeline processes and validates products through the different phases while preserving their source-level information.

Phase 7 would build on these outputs and bring together all rows from all supported brands and retailers into a common integrated layer.

The main objectives of Phase 7 would be to:

  • merge the processed outputs from all brands and retailers into a unified dataset;
  • identify products that represent the same underlying product across different retailers or sources;
  • extend the existing product-group and identity concepts across sources;
  • preserve the original retailer, brand, source ID, and provenance information for every record;
  • avoid losing source-specific information when records are integrated;
  • produce a unified cross-retailer representation that can be consumed by downstream applications and analysis;
  • introduce stable group and variant identifiers that survive the addition of new products;
  • and prepare the Reference DB for the type of group-level integration and merged product representation that is being developed for the Open Food Facts Open DB.

This phase is intentionally left as future work because the current implementation focuses on building and validating the individual processing phases and their outputs.

Phase 7 would operate on top of these validated outputs rather than replacing the existing phases.

22.2 Group-Level Data Merging

Another important future improvement is to introduce a richer group-level representation where information from multiple variants and sources can be merged into a canonical product-group record.

The current pipeline keeps variant-level records separate and preserves their source information.

Future work could add a canonical group-level layer that combines compatible information across those records while maintaining full traceability to the original sources.

22.3 Broader Source Coverage

The adapter architecture can be extended to additional brands and retailers by implementing the retailer adapter interface for each source (starting with the existing Costco, Metro, Voilà, and Walmart placeholders).

Retailer-specific schemas and transformations stay in the adapters, so the downstream processing logic can remain source-independent.

22.4 Improved Entity Resolution

Future iterations could improve cross-source entity resolution by:

  • adding more curated edge cases;
  • expanding regression datasets;
  • improving candidate generation (for example order-insensitive blocking);
  • evaluating false merges and false splits quantitatively;
  • and validating grouping decisions across a broader range of brands and retailers.

22.5 Additional Data Quality and Enrichment

Future work could also include:

  • obtaining or deriving FVL data from ingredients so that final Nutri-Score grades can be published;
  • adding Nutri-Score rules for beverages and special food categories;
  • extending the Agribalyse mapping, including exact product-level matches where defensible;
  • improving nutrition completeness where source data is available;
  • carrying the original size field through Phase 1;
  • adding more automated checks and unit tests for Phases 1, 2, 4, 5, and 6;
  • making the data contracts executable and wiring the review/quarantine workflow into the pipeline;
  • and monitoring pipeline changes over time (see also pipeline orchestration below).

22.6 Pipeline Orchestration

Currently each phase is run as a separate step. A future improvement is to add orchestration so the full pipeline (ingestion through production outputs) runs as one managed workflow, with explicit phase dependencies, scheduling, retries, failure handling, and monitoring. This would also make it easier to run the pipeline for multiple retailers and to resume from the phase where a failure or ambiguity occurred.

23. Lessons Learned

This project taught me lessons beyond the implementation itself. Working on a real open-source data problem changed how I think about requirements, architecture, validation, and the relationship between an initial plan and the final solution.

Technical and Design Lessons

Separate Identity from Variants

A product group should represent the underlying product identity, while variant-level differences should remain explicit. This distinction became important when dealing with different package sizes and other product attributes.

Do Not Rely on a Single Identity Signal

UPC, product title similarity, brand, or a single normalized field are not sufficient on their own to determine product identity. Product grouping requires combining multiple signals and explicit decision rules.

Similarity Is Not Proof

Similarity is useful for generating candidates, but it should not automatically determine that two products belong to the same group. A candidate still needs an explicit identity-based decision.

Preserve Source Truth

Source values should not be silently rewritten, merged, or fabricated. Normalized and enriched representations should be added on top of the source data while maintaining traceability to the original record.

Treat Ambiguity Explicitly

Not every case can be safely resolved automatically. When the available evidence is insufficient, it is better to represent the case as ambiguous and send it for review than to force an incorrect decision.

Validate Each Stage

Validation needs to happen throughout the pipeline rather than only at the end. Checking identifiers, row counts, relationships, schemas, and phase outputs close to where problems occur makes debugging and maintenance much easier.

Project and Professional Lessons

Be Flexible About the Solution

One of the most important lessons I learned was that I should not become attached to an earlier implementation just because I had already invested time in it.

As the requirements and my understanding of the problem evolved, some parts of the project needed to be redesigned rather than continuously patched. I learned to keep the goal stable while allowing the implementation to change when the evidence justified it.

Understand the Consumers

A technical solution should start with understanding who will use it and what they actually need.

For the Reference DB, this means thinking about maintainers, future contributors, downstream applications, and people consuming the resulting datasets. This affected decisions about what information to preserve, what to normalize, how to structure outputs, and how much complexity was actually useful.

Real-World Data Changes the Problem

The initial project plan gave me a direction, but working with real data exposed constraints that were difficult to predict beforehand.

I encountered incomplete and inconsistent source data, source protection, unreliable identifiers, ambiguous product identities, and differences between source representations. This taught me to treat early assumptions as hypotheses and validate them against real data.

A Plan Is a Starting Point, Not a Fixed Specification

The project evolved as I learned more about the data and the needs of the project.

I learned that following the original plan literally is not always the best way to achieve the original goal. Sometimes the right way to move forward is to change the structure of the solution while preserving its purpose.

Working Code Is Not the Same as a Finished Contribution

A pipeline can run successfully and still be difficult for someone else to understand or maintain.

I learned that documentation, reproducibility, provenance, validation, clear phase boundaries, and explicit limitations are part of the contribution, not things to add after the code is finished.

Be Honest About Scope

Another important lesson was learning to distinguish between what is implemented, what is validated, what is partially prepared, and what remains future work.

For an open-source project, making these boundaries explicit is more useful than trying to present everything as complete. It gives future contributors a clear starting point and makes the current state of the project easier to evaluate.

Feedback Is Part of the Development Process

Review and discussion are not only useful at the end of a project.

During the project, feedback and new findings changed how I understood some of the design decisions. I learned to treat review as part of development and to use it to improve the architecture rather than only to correct implementation details.

25. Final Summary

This project established the foundation for a Canadian Reference DB pipeline capable of transforming heterogeneous food-product sources into a structured and traceable data model.

The work went beyond a single dataset or scraper.

It established:

  • a reusable retailer-adapter architecture and shared ingestion layer;
  • clear boundaries between source-specific logic and processing phases;
  • standardized product representations;
  • identity normalization;
  • product grouping with explicit ambiguity handling;
  • variant modeling;
  • rule-based taxonomy and classification layers;
  • nutrition integration, Nutri-Score components, and category-level Agribalyse mapping;
  • production outputs;
  • automated validation;
  • versioned data contracts and quality statuses;
  • and documentation for future contributors.

The current implementation is validated on the Compliments dataset, while the broader collection work provides additional source datasets that can be progressively connected to the architecture.

The next major extension is Phase 7 — Cross-Brand and Cross-Retailer Integration, which would build a unified Reference Database across all supported sources while preserving retailer, brand, source identifiers, and provenance.

The resulting system is intended to serve as a foundation that future contributors can extend with new sources, improved entity resolution, stable identifiers, group-level canonical merging, cross-source integration, complete Nutri-Score grading, and additional downstream use cases.
